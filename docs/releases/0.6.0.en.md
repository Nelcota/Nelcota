# Nelcota 0.6.0 — 2026-11-04

## Reviewed settings and transactional emails

- Host operators can edit project auth/session, API/performance and file limits
  in one reviewed batch, with a source revision, non-secret impact summary, one
  application restart and configuration-only recovery. The panel compares saved
  settings with effective startup values and refuses incompatible applications.
- Public API CORS can use an exact-origin allowlist. The default remains any
  origin; an explicit empty list allows none. Panel same-origin protections and
  JWT/RLS remain independent.
- Authentication emails support English/Portuguese, bounded plain-text subjects
  and messages, validated placeholders and configurable confirmation/recovery/
  magic-link lifetimes. Existing links retain their original expiration.
  Fictional previews issue no credentials. SMTP tests go only to the configured
  administrator and share a one-minute attempt budget.

See [project settings](../host-management.md#project-settings-in-the-current-checkout) and
[email templates](../email-templates.md).

## From local development to deployment and recovery

- Scoped, expiring and revocable deployment tokens support repository migrations
  through the project API, named environments, status/dry-run and TypeScript
  downloads. The panel previews/applies uploaded migration files and guides
  deployment, access verification and recovery without equating health with a
  successful data-restore rehearsal.
- A project-scoped Linux backup agent captures and verifies database/disk-file
  backups before production migrations, with external readback when configured
  and durable fencing across cancellation/recovery. Enable it explicitly; merely
  upgrading does not configure the agent or offsite storage.
- `nelcota dev` owns its PostgreSQL container by canonical project path, applies
  and watches application migrations, and offers a confirmed local database
  reset. `dev --mail` adds a private Mailpit inbox with verified STARTTLS.
  Native Windows local mail has an extended-path/OpenSSL/Docker mount limitation;
  use Linux for that optional workflow.
- `nelcota update` previews and updates the CLI and projects in one flow,
  preserving the previous CLI and existing backup/rollback behavior. Enrolled
  hosts keep their separate controller update workflow.
- The panel has a persistent avatar editor, clearer navigation and access-policy
  review, corrected row targeting, pagination, JSON-null editing and exports.

See [remote migrations](../remote-migrations.md), [updates](../update.md) and
[the complete server changelog](../../CHANGELOG.md).

## Security and resource isolation

Signup confirmation binds password retention to the originating client's S256
PKCE proof, retires unverified credentials and avoids revealing account existence
when confirmation is enabled. Refresh retries reuse the same successor during
the grace window. Panel sign-out/expiry clears private SQL history and drafts.

REST/storage have default rate limits and per-caller concurrency budgets.
Dropped REST requests cancel their database statement; reads use read-only
transactions. Catalog/OpenAPI visibility respects column grants, and unsafe
inheritance children are not exposed without their own RLS. Uploads enforce
per-caller, idle and sustained-progress limits. Webhook queue overflow no longer
aborts application writes, and fair claims prevent one slow destination from
starving others. Signed file URLs are bound to the signed object version.

## Before upgrading

1. **0.5.6 → 0.6.0 applies V17–V22**, advancing internal schema V16 to V22:
   deployment tokens/audit, private avatar editor data, webhook queue/fair-claim
   changes, encrypted refresh successors and signup PKCE binding. Allow a
   maintenance window and rehearse on representative data. Never edit released
   SQL/checksums. Install the matching CLI before application/controller updates.
2. Take and restore-test a **paired database/file backup**. Keep the previous
   binary/image and pre-upgrade backup together. A manual downgrade requires the
   compatible database and file snapshot, not just an older executable.
3. **Reissue signed file URLs.** Links issued before this upgrade lack a version
   binding and return `403 invalid_signature`; old links must not expose newly
   replaced file contents.
4. Review `NELCOTA_API_RATE_LIMIT_PER_MINUTE` (**600 by default**, `0` disables),
   proxy trust/hops and per-caller concurrency/upload budgets. Anonymous SSR
   traffic or an untrusted proxy may share one address budget. Read-only REST
   requests can no longer invoke writing functions through a view or policy.
5. **Email confirmation needs signup PKCE to retain the chosen password.**
   Without that proof, confirming claims the account but clears its signup
   password; set a password while authenticated or use recovery. Confirm your
   application's SDK/flow before enabling confirmation. Server publication does
   not deliver source-only SDK PKCE changes to registry consumers.
6. Rust auth/core consumers must adapt `trust_proxy: bool` to `proxy_hops: u8`
   and the changed state/config constructors. This minor version does not publish
   auth/core crates. API/storage timeout values are capped at one day, and
   production refuses `NELCOTA_WEBHOOKS_ALLOW_LOOPBACK=true`.

## Artifacts, verification and limits

The official workflow publishes checksum-protected Linux amd64/arm64 musl
binaries, `ghcr.io/nelcota/nelcota-server:0.6.0`, signed build provenance and a
signed readiness manifest tied to the exact source and green main CI. Verify
availability, checksums and attestations on the
[release page](https://github.com/Nelcota/Nelcota/releases/tag/v0.6.0).

Candidate/released-binary acceptance reports must identify their SHA-256 and
source; see [the release handoff](../onboarding/release.md). Earlier reviews and
load reports retain their original scope. This release does not claim a new
long soak, native ARM run, production VPS/systemd, public DNS/TLS, external inbox
delivery, application S3 migration or PITR acceptance.

TypeScript **0.2.5**, Rust **0.1.7**, Next.js **0.1.2** and SSR **0.1.0** keep
independent package versions and publication gates. SDK changes mentioned in
the repository changelog remain source-only until separately released.
Publishing this server neither updates client dependencies nor deploys a host.
